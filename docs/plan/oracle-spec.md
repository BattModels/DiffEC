# Oracle Spec

> **The authoritative governing equations are in `docs/proposal/formalism.md`
> §2 (eqs 7-8 of Chen et al. 2026).** This file pins the *numerical*
> realization — discretization, sign conventions, BC/IC enforcement, and
> the canonical flux decomposition — so case generation and the verifier's
> self-consistency check (#6) cannot disagree.
>
> Starting point: `Mass Transport in Concentrated Electrolytes and Benchmarks/solver.py`.

## 1. Frame, signs, and the moving boundary

The PDEs are written in the **moving electrolyte frame**. The frame
co-moves with the deposition electrode at `x = 0`:

- `x ∈ [0, L]` with `x = 0` at the (instantaneously) plated electrode.
- `v₀(x, t)` is the **solvent velocity in this moving frame**. Sign convention: `v₀ > 0` ⇒ solvent moving in the `+x` direction (away from the plating electrode).
- The cation flux at both boundaries equals `i_app(t) / F` (deposition consumes salt at `x = 0`, stripping produces it at `x = L` — or vice versa; pick one and pin it). The current schedule is supplied as a tabulated `i_app(t)`.

The lab vs moving-frame distinction is *the* central scientific point of
the task. Document any sign / direction convention exactly once here and
quote it verbatim into `formalism.md`. Do not re-derive elsewhere.

## 2. Governing PDEs (numerical form)

We solve the proposal's eqs 7-8:

```
∂c/∂t  = ∂/∂x [ D(c) (1 − d ln c₀ / d ln c) ∂c/∂x  −  t⁺⁰(c) i(t) / F  −  c v₀ ]
∂v₀/∂x = V̄(c) ∂/∂x [ D(c) (1 − d ln c₀ / d ln c) ∂c/∂x  −  t⁺⁰(c) i(t) / F  −  c v₀ ]
```

Both equations share the bracketed term `F(c, v₀; i, t)` — the cation
flux. The numerical scheme exploits this:

- Compute `F` once per timestep on cell interfaces (face values).
- Concentration update: `c_{n+1} = c_n − (Δt/Δx) (F[1:] − F[:-1])`. First-order forward Euler in time (matching `solver.py`); cell-centered `c`; face-centered `F`.
- Velocity update: integrate the second PDE in space — `v₀(x) = ∫₀^x V̄(c) ∂F/∂x' dx'`. In the discrete scheme this is a cumulative sum of `−V̄ · (F[j] − F[j−1])` across interior faces; `v₀` lives on faces, with `v₀[0]` set by the moving-boundary condition and `v₀[N]` falling out from the integral.

This matches `solver.py` exactly. Do not silently switch to centered
differences, implicit time-stepping, or staggered grids — the verifier's
self-consistency check (#6) runs *this* scheme, and the case ground
truth was generated by *this* scheme.

## 3. The `t⁺⁰_NE` inversion (formal definition)

`t⁺⁰_NE(c)` is the transference number that *would* be inferred under
classical Nernst-Planck — i.e., ignoring solvent motion entirely. The
proposal's `formalism.md` §3.2 gives the variational form:

```
t⁺⁰_NE(c) = argmin_{tp0} || c_sim − c_data ||
              subject to:  ∂c/∂t = ∂/∂x [ D(c) ∂c/∂x − tp0(c) i/F ]   (v₀ ≡ 0)
                           tp0 evaluated at the same c_grid points
                           D(c) = the agent's reported D(c) at c_grid points
```

Pinned details:

- The inversion is run **once per case** by `oracle/invert_ne.py` during
  case generation, using the oracle's *true* `D(c)` to remove ambiguity.
  The resulting `t⁺⁰_NE_oracle[50]` is written into `truth.npz`.
- The agent computes its own `t⁺⁰_NE` from its own `c_data` fit using
  its own `D(c)`. The verifier compares the resulting regime labels
  (check #3), not the `t⁺⁰_NE` values themselves — agents with slightly
  different `D(c)` won't be penalized for slightly different
  `t⁺⁰_NE` magnitudes, only for sign / NE_deviates mis-classification.
- The inversion is solved by the same gradient-based BFGS used in the
  forward inversion, on a 50-parameter `t⁺⁰_NE(c)` ansatz (one free
  value per c_grid point with light Tikhonov regularization). This
  matches what an honest agent would do.

## 4. Flux decomposition convention

`oracle/flux.py` defines the canonical decomposition (per ADR-0003):

```
J_diff(x, t) = − D(c) · (1 − d ln c₀ / d ln c) · ∂c/∂x
J_mig (x, t) =   t⁺⁰(c) · i(t) / F
J_conv(x, t) =   c · v₀
J_total      =   J_diff + J_mig + J_conv
```

Units throughout: `mol / (m² · s)`. Signs as written; `v₀` is the
moving-frame velocity from §1.

Both `case_gen/` and `tests/test_flux.py` import this function. The
agent's reference solution imports a deliberately separate copy under
`reference_solution/`, to prove that a clean-room implementation can
match the convention by reading `formalism.md` alone.

## 5. Boundary and initial conditions

- **Boundary (both ends):** `F_face = i_app(t) / F`. Implemented by
  setting `F[0]` and `F[-1]` directly before the central-difference
  update for `c`. This is what `solver.py` already does (`F_left`,
  `F_right`).
- **Moving boundary on `v₀`:** `v₀(x = 0, t)` is set by the volumetric
  balance of deposition: solvent is displaced by the plated metal at
  the electrode. In the discretized cumulative-sum form, `v₀[0] ← 0`
  and the cumulative sum sets the interior values; the rightmost face
  `v₀[N]` falls out and is reported but not constrained. This matches
  `update_solvent_vel` in `solver.py`.
- **Initial conditions:** uniform `c(x, 0) = c_init` (per-case), and
  `v₀(x, 0)` set by `V̄(c) · (1 − t⁺⁰(c)) · i(0) / F` — also matching
  `solver.py`.

## 6. The `(1 − d ln c₀ / d ln c)` factor

Tabulated per case from a `rho(c)` polynomial. The proposal allows for
this to vary between cases (each `params.json` ships its own table).
In the oracle we keep the same functional family as `solver.py`
(`rho(c) = a + b c + d c²`, with `(a, b, d)` per-case) but allow the
coefficients to differ from the published PEO-LiTFSI fit (ADR-0004).

`oracle/solver.py` consumes the tabulation as `(c_table, factor_table)`
arrays and `jnp.interp`s on demand. The agent receives the same
tabulation in `params.json` and is expected to do the same.

## 7. Determinism contract

- All RNG is `numpy.random.default_rng(seed)`. Seeds live in
  `case_gen/configs/case_X.yaml`.
- JAX float64 (`jax.config.update("jax_enable_x64", True)`) is on
  globally. CPU backend only (`JAX_PLATFORMS=cpu`).
- Output arrays are saved as float64 in `truth.npz` and `data.h5`. No
  silent downcast.
- Repeating `case_gen/generate.py --case case_X` on the same machine
  must produce byte-identical artifacts. CI grep-checks this on each
  PR commit.

## 8. Smoke test

Before any case is generated, `scripts/smoke_test.py` reproduces the
published Steinrück-2020 fit by running the oracle solver with the
published PEO-LiTFSI parameters, then checks two things:

- **Primary (acceptance gate).** Max-relative error vs the published
  solver's own saved output (`results/c_sim.npy`) at all 9 sampled time
  indices, all 50 cells: `< 1e-3`. In practice we observe `~3e-16`
  (machine-precision identity), which says our generalized solver
  preserves the published solver's numerics bit-for-bit. This is the
  rigorous check called out in ADR-0002.
- **Secondary (informative only).** Max-relative error vs the
  experimental `c_data` interpolated onto the oracle's mesh: typical
  values `~6 %` mean / `~9 %` worst-point. **This is the published
  fit's own residual against experiment, not a property of the solver.**
  We log this number for tolerance-calibration context (it bounds how
  tight any case's `D(c)`/`t⁺⁰(c)` tolerance can sensibly be against
  noisy data) but do not gate on it.

If the primary check fails, the solver has a bug; do not generate cases
until it passes.
